How to Pull a Million Records from an API Without Losing One

A page-size cap of 1,000 is not a bug. It is the API protecting itself. This page shows why a pull takes an hour, which lever actually moves that number, and which loops drop or repeat rows.

Offset drift versus a keyset cursor

The strategies

Naive. One call. The server returns HTTP 400, or it silently stops at the page cap. You have 1,000 rows and you think you have the table.
Offset. Skip N, take a page, add the page size, repeat. Easy to write. Slow at depth, because the database walks the skipped rows. Wrong if rows are inserted, deleted, or re-sorted while you page.
Cursor. The server hands you an opaque token for the next page. Consistent, and impossible to parallelize, because you cannot invent the next token.
Keyset. WHERE id > last_id. The index seeks. Depth does not matter. You can also cut the id space into ranges and run those ranges together.
Parallel offset. Pages are independent, so threads help, until the rate limit starts returning 429. In this lab's demo, 20 threads against a 5 request/second cap produced 30 retries. A client limiter at 4/second produced zero.
Partitioned keyset. The usual production shape. Split by id or date, seek inside each split, cap concurrency, honor the rate limit.
Resilient. Retries, Retry-After, jitter, a client-side token bucket, and a checkpoint after every page. A hard kill resumes without duplicating finished pages.
Incremental. Save the server clock from the start of the run. Next run asks for updated_since. The first load is the slow one.
Bulk export. If the API will write you a file, take the file. You pay for a handful of calls, not for every page.
